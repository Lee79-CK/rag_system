1. 한눈에 보기 처음 보는 분을 위한 그림

이 시스템은 회사 문서를 근거로 답하는 사내 챗봇입니다. 일반 AI 챗봇과 달리, 관리자가 미리 넣어 둔 문서에서 근거를 찾아 그 내용만으로 답하고, 어느 문서의 몇 쪽을 참고했는지 표로 함께 보여 줍니다.

도서관에 비유하면 — 관리자는 책을 들여와 쪽마다 색인 카드를 만들어 두는 사서(②), 사용자가 질문하면 색인 카드로 관련 쪽을 찾아(근거 찾기) 그 쪽만 읽고 요약해 주는 상담원(답변 작성)이 있는 셈입니다. "색인 카드"가 벡터, 카드 보관함이 Qdrant, 요약하는 상담원이 LLM(vLLM)입니다.
  • RAG(Retrieval-Augmented Generation): 먼저 찾고(Retrieval) 찾은 내용을 넣어 답을 만든다(Generation). AI가 모르는 사내 내용도 근거 있게 답하는 방식.
  • 답변은 한꺼번에 나오지 않고 글자가 만들어지는 대로 화면에 나타납니다(스트리밍).
  • 근거를 찾지 못하면 지어내지 않고 "근거 부족"으로 답합니다.

2. 채널 격리 누가 어떤 문서를 근거로 받나

대화방(채널)마다 볼 수 있는 문서가 정해져 있습니다. 문서를 올릴 때 "허용 채널"을 지정하면, 그 채널에서 한 질문만 그 문서를 근거로 쓸 수 있습니다.

  • 검색은 반드시 build_filter()로 채널 조건을 먼저 걸고 실행합니다(찾은 뒤에 거르는 방식 금지) — 다른 채널 문서는 후보에도 오르지 않습니다.
  • 문서를 [비활성화]하면 is_active=false가 되어 어느 채널에서도 검색되지 않습니다.
  • 격리 정확도 100%는 배포 차단 테스트(CH-001~010)로 매번 검증합니다.

3. 하드웨어 아키텍처 물리 서버 2대

역할을 나눴습니다. P3는 화면·API·검색 모델·데이터베이스를 모두 맡는 "본체", PGX는 GPU로 답변 문장만 만드는 "AI 전용기"입니다. 두 대는 사내 LAN으로 연결되고 인터넷에는 연결되지 않습니다.

  • 왜 DB 전용 NVMe를 따로? 검색(Qdrant)·DB는 작은 읽기/쓰기가 많아 HDD에서는 느립니다. OS 디스크와 분리해 두었기 때문에 DB가 커져도 OS 디스크가 차서 노드 전체가 멈추는(DiskPressure) 일이 없습니다. 대신 두 NVMe(/, /data/fast)의 여유 공간을 각각 감시해야 합니다.
  • 왜 임베딩·리랭커는 CPU? GPU 1장은 LLM 전용(ADR-009/010). 그래서 대용량 문서 색인은 CPU 속도에 묶입니다(그림 7 참고).

5. 소프트웨어 아키텍처 계층과 구성요소

브라우저 요청은 ingress-nginx를 거쳐 화면(정적)과 API로 나뉩니다. 오래 걸리는 RAG 처리는 API가 직접 하지 않고 큐(Redis)에 넣어 worker가 처리합니다 — 질문 접수는 1초 안에, 답변은 그 뒤 스트리밍으로.

구분기술
백엔드Python 3.12 · FastAPI · python-socketio · SQLAlchemy 2 + Alembic · RQ · structlog · Prometheus client (uv workspace 모노레포)
프런트엔드chat-web: Next.js 15 · React 19 · TanStack Query · zustand / admin-web: React 18 · Vite · antd
AIvLLM (OpenAI 호환) · Qwen3.8-27B-FP8 · KURE-v1 임베딩 · bge-reranker-v2-m3 · FlagEmbedding
데이터PostgreSQL 16 · Redis 7 · Qdrant 1.12
인프라RKE2 v1.34 · containerd · Canal(CNI) · ingress-nginx · local-path-provisioner · NVIDIA GPU Operator · Helm

설계 원칙 (요약)

  • 폐쇄망: 실행 중 외부 네트워크 호출 없음 — 모델·패키지·폰트 모두 미리 반입, 로컬 경로에서만 로딩.
  • 계약 한 곳: 서비스 간 데이터 형식은 libs/schemas(rag_schemas)에서만 정의. 앱끼리 직접 import 금지.
  • 보안 기본값: 비밀번호 원문은 서버로 오지 않음(브라우저에서 PBKDF2 prehash). Secret 파일이 없으면 기동은 하되 로그인·피드백을 거부(fail-closed).
  • 중복 방지: worker는 claim_job(QUEUED→RUNNING 원자 전이)에 성공한 작업만 처리 — 같은 답변이 두 번 쓰이지 않음.

6. 질문 한 건의 처리 순서

사용자가 [전송]을 누른 순간부터 답변이 확정될 때까지의 흐름입니다. ①~④가 "접수", ⑤~⑯이 "백그라운드 처리"입니다.

  • gateway가 여러 개여도 Redis pub/sub으로 모든 gateway에 이벤트가 전달되므로, 어느 gateway에 접속했든 같은 채널 화면에 글자가 나타납니다.
  • 리랭커가 느리면(45초 초과) 벡터 검색 순서로 대체해 답변을 계속합니다(로그 worker.rerank_fallback).
  • 답변의 최종 원본은 PostgreSQL의 Bot Post입니다. 스트리밍 글자는 화면 표시용(유실돼도 최종 저장본으로 확정).

7. 문서 색인 파이프라인

문서를 올린 뒤 검색에 쓰이기까지의 과정입니다. 무거운 작업이라 서비스와 분리된 일회성 K8s Job으로 실행하고, 한 번에 하나씩 처리합니다.

  • 같은 내용(sha256)의 문서는 중복으로 거부되고, 기존 문서에 채널만 추가하도록 안내합니다.
  • 재색인하면 새 버전을 만든 뒤 검증이 끝나야 이전 버전을 내립니다 — 색인 중에도 기존 답변은 계속 동작합니다.
  • 스캔(이미지) PDF는 OCR이 꺼져 있어 색인되지 않습니다. 일부 쪽만 이미지면 그 쪽만 빠집니다.
